| S-07 | **Resolved 2026-11-01**, by the precedence change recorded in [Appendix D](appendix-d-mathematical-challenges.md) section 1.0.1: the example governs the mathematics, so the code changed rather than the requirement. The convention is now world-frame linear and body-frame angular, translation-first, and a force-free body conserves world linear momentum to below 1e-14 against the 3.93e-3 drift that was measured before. Original question: the implemented `Free` joint stores its linear velocity in the **body** frame; [Step 01](01-state-and-coordinates.md) item 3 MUST-requires the reference asymmetry (world-frame linear, body-local angular). Change the representation to match the requirement, or amend item 3 and record the local convention as a deviation? (Appendix D [M-01](appendix-d-mathematical-challenges.md#m-01)) | Any claim that step 01's "Done when" is met, and the energy-conservation oracles of [Step 04](04-fidelity-loop.md) for free-floating bodies | Treat the requirement as governing and the code as out of agreement, which is the change-control default. The audit measured the cost of the current convention — 0.39 % world linear-velocity and 0.14 % kinetic-energy gain per simulated second on a force-free isotropic spinning body at `dt = 1e-4`, with controls isolating the convention as the cause — so the decision can be taken against a number rather than a preference. Note that a higher-order orientation update reduces but does not remove it: under the required convention the drift is identically zero for any spin, because there is no `-omega x u` cancellation left to integrate |
| S-08 | **Resolved 2026-11-01**: the eigenvalue condition was adopted, as the interim position proposed, with a tolerance relative to the largest principal moment because an exact test rejects a thin rod on rounding alone. The stronger pseudo-inertia realisability condition remains open as its own question, and the deviation is documented at the call site. Original question: `InertiaTensor::is_physically_plausible` tests the triangle inequality on the diagonal entries only and so accepts an indefinite tensor. Adopt the eigenvalue (principal-moment) triangle inequality, or the stronger 4x4 pseudo-inertia realisability condition over mass, centre of mass and tensor jointly? (Appendix D [M-03](appendix-d-mathematical-challenges.md#m-03)) | Closing the defect, and [Step 05](05-passive-forces-and-actuators.md) item 2, which names this function as the pattern its own sign-preservation check should follow | Adopt the eigenvalue condition first: it is the minimal correct fix, is a closed-form or short Jacobi sweep in plain `f64` inside the purity contract, and rejects the measured counterexample. The pseudo-inertia condition additionally rejects a mass/COM/inertia triple that is individually plausible but jointly impossible; it is a larger change and should be its own decision. The two reject different inputs, so whichever is adopted must be recorded |
| S-09 | **Resolved 2026-11-01**: treated as one change, as the interim position proposed. `solver` refers every row's impedance to its own exact `A_ii` and the per-point penalty law is gone, replaced by the exact bounded plane manifolds of example `04`. Original question: does the contact path adopt the example's `A_ii`-proportional impedance (`R = max(MINVAL, (1 - imp) * A_ii / imp)`), which [Step 06](06-equality-constraints-and-solver.md) item 2 requires and which `constraint::solve_equality` already implements for equality rows — replacing the fixed `CONTACT_REFERENCE_MASS = 1.0` and the per-point penalty law together? (Appendix D [M-09](appendix-d-mathematical-challenges.md#m-09), [M-04](appendix-d-mathematical-challenges.md#m-04)) | Whether M-04 and M-09 are fixed separately or as one change, and therefore the sequencing of most of step 06 | Treat them as one change. M-04 (contact stiffness scaling with the number of sampled points) and M-09 (impedance referred to a constant mass) are both symptoms of a per-row penalty law with no notion of the row's own effective mass; the example's formulation addresses both, and the diagonal of the matrix `contact_externals` already assembles *is* the `A_ii` it needs. Doing them separately risks tuning around M-04 with a point-count correction that the M-09 fix would then invalidate |
| S-10 | What does the project do about a model whose declared actuator gains are evidently generated defaults rather than the robot's own tuning? The G1 layer sets `damping = 0.0004 x stiffness` on all 29 drives to float precision with `targetPosition = 0`, giving a damping ratio of 0.003 to 0.03 at up to 13183 N m/rad. Applying them is faithful to the asset and is what a simulator reading `PhysicsDriveAPI` does; the resulting robot is rigid and almost undamped. (Appendix D [M-28](appendix-d-mathematical-challenges.md#m-28)) | Whether a named fidelity tier ([Step 09](09-fidelity-tiers.md), S-03) fixes an actuation mode, and what `robot sim multibody`'s default should be | Keep applying the declared drives as the default, because deviating from the asset silently is worse than reporting it, and make the alternative one flag away: `ActuationMode::{Drives, Damping, Zero}` exists and `World::drive_gains_look_generated` reports the uniform ratio in the run output. What is **not** settled is whether a tier should pin a mode, and whether the project should carry a published G1 gain set as a separate, declared override rather than editing the vendored layer. Do not edit the vendored asset: it is the standard this project is checked against |
| S-11 | Mesh collision: convex hull per mesh prim, or convex **decomposition** for the concave shells a humanoid's torso actually is? Example `04` and `08` both assume a hull, and the example's own compiler builds one hull per mesh at compile time; a single hull of the G1's torso shell is a coarser shape than the shell, though far tighter than the axis-aligned box standing in for it today. (Appendix D [M-27](appendix-d-mathematical-challenges.md#m-27)) | [Step 07](07-collision-pipeline.md) item 2 and [Step 08](08-model-compilation-and-sensors.md) item 3, both MUSTs, and therefore any contact claim involving a link the G1 describes only by mesh | Build one hull per mesh prim first, matching the example and closing both MUSTs, and measure before considering decomposition. `collision::gjk_epa` already accepts any shape that answers a support query, so a hull is a vertex cloud and `argmax_i (v_i . d)`; the cost is a compile-time hull build, which [Step 08](08-model-compilation-and-sensors.md) already owns. Decomposition is a larger change with its own parameter set and should not be entered without a measured case that the single hull is insufficient |
