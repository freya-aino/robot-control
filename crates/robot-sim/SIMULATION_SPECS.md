## 0. Purpose and how this document was built

The project's target changed, by explicit direction, partway through implementing `robot-sim`'s multi-body dynamics solver: the simulator must become **GPU-bound and batched** (thousands of parallel environments, not one instance), support **variable fidelity** (a caller trades accuracy for speed, not a single fixed-quality engine), stay **as close to Rust-native as possible** (minimal FFI, no foreign runtime — continuing `SPECS.md` Section 2's standing policy, not an exception to it), and be designed so the simulation backend is **agnostic to every other component** — training, control, viewing, the CLI — which depend on an interface, never on a backend's internals.

"On par with MuJoCo" is the stated fidelity target. Sections 1-10 below are therefore grounded in direct research against MuJoCo's own source and documentation, not its marketing description: a research agent read `google-deepmind/mujoco` at pinned commit `800a109a4bdd02cb60404d565db4ae16fb04a53b` (tag `3.17.0`), the `mjx` subdirectory of the same repository, `huggingface/candle`, `tracel-ai/cubecl`, `gfx-rs/wgpu`, `google/brax`, `isaac-sim/IsaacLab` and `dimforge/rapier`, each at whatever commit was current on 2026-10-26. Appendix A is the condensed citation ledger; inline citations below use the short form `[MuJoCo §N]` / `[MJX §N]` / `[Brax §N]` / etc. pointing at Appendix A's numbered entries. Every claim about a third-party system carries the evidence-state tag that table licenses — most are `code_inspected` (source/docs read directly) or explicitly flagged `secondary`/`unverified` where the research agent could not confirm something first-hand. Claims about *our own* system start at `unverified` like everything else in this project and are promoted only by the tests Section 14 requires.

## 1. Target and explicit non-goals

### 1.1 "On par with MuJoCo" — what this binds

A `robot-sim` physics backend claiming parity with MuJoCo MUST, at minimum, address every subsystem MuJoCo's own engine treats as load-bearing (Sections 4-10): generalized coordinates including a floating base, a mass-matrix/bias-force dynamics pass, a constraint solver that handles contact and equality constraints as one problem, a multi-stage collision pipeline, actuators with a real transmission/gain/bias model, and an integrator family that remains stable on stiff systems. "On par" does not mean bit-identical, require MuJoCo's own exact algorithms where a documented alternative is better suited to a GPU-batched, Rust-native implementation (Section 11 makes exactly this call for the solver's batching strategy), and does not require feature parity with MuJoCo's biology-oriented extensions (muscle activation dynamics) or its deformable-object machinery (`flex`, 1D/2D/3D soft bodies) — both are explicit non-goals under 1.6.

### 1.2 GPU-bound, batched execution

The primary execution mode MUST be thousands of environments stepped in parallel on a GPU, following the precedent of MJX and Brax (Appendix A entries 12, 13, 17) rather than this project's existing CPU-only, single-instance `robot_sim::articulated::ArticulatedBody`. Section 11 specifies the batching architecture. A CPU reference backend remains REQUIRED regardless (Section 11.4) — not as the primary execution mode, but as the correctness oracle the GPU backend is checked against, exactly as MJX-JAX's own test suite is checked against CPU MuJoCo [MJX §12].

### 1.3 Variable fidelity

The engine MUST expose fidelity as a tunable, queryable property of a simulation run, not a fixed characteristic of the backend. Section 12 enumerates the specific knobs (integrator, solver iteration budget, contact dimensionality, contact-slot budget, timestep) and proposes named fidelity tiers as this project's own addition — research found no existing named-tier concept in MuJoCo itself [MuJoCo §15], only an unnamed pile of independent knobs, so this is a deliberate design decision, not an inherited one.

### 1.4 Rust-native-first

No foreign runtime, no FFI to C/C++/CUDA-as-a-foreign-language, and no MuJoCo binding, continuing `SPECS.md` Section 2's standing exclusion rather than creating an exception to it. "As close to Rust-native as possible" is read as: author GPU kernels in Rust (via CubeCL) where feasible, fall back to hand-written WGSL compute shaders via `wgpu` (still Rust-hosted, still no foreign toolchain beyond the GPU driver) where CubeCL cannot express the needed control flow, and treat any C/CUDA-authored kernel as a foreign-dependency exception requiring the Section 2.1 procedure, not a default path. Section 11.3 details the specific candidates and their risks.

### 1.5 Backend-agnostic / plug-and-play

Every crate outside `robot-sim` that consumes a simulated environment (`robot-learn`, `robot-control`, `robot-viewer`, `robot-cli`, `robot-tasks`) MUST depend only on a stable environment interface, never on a physics-backend-specific type. Section 13 specifies the two-layer boundary this requires, modeled directly on Brax's `Env`/`PipelineEnv` split [Brax §17] — the clearest, most concrete precedent research found for exactly this separation.

### 1.6 Explicit non-goals for this revision

- Muscle/biological actuator models (MuJoCo's `MUSCLE` gain/bias/dynamics type) — not relevant to a rigid-actuator humanoid.
- Deformable objects (`flex`: cloth, rope, soft tetrahedral bodies) and signed-distance-field collision geoms — genuinely still "under development" in MuJoCo itself as of the pinned commit [MuJoCo §11], and out of scope for a first humanoid-locomotion target.
- Differentiability (gradients through the physics step) — MJX-JAX has this via JAX autodiff, MJX-Warp explicitly does not [MJX §17]; this revision does not require it of either `robot-sim` backend, though Section 13.3 names it as a capability that MAY differ by backend later and must be declared, not assumed.
- A rendering/visualization path — `robot-viewer` remains the data-layer-only crate it already is; nothing here requires or implies a GPU rasterizer.
- Floating-base *URDF* joints. `robot_model::urdf` continues rejecting `floating`/`planar` joint types in imported URDF by name (`docs/decisions/0002`); Section 3's floating-base requirement is a `robot-model`/`robot-sim` **simulation-time** construct, added as a new `JointKind` variant, not a relaxation of what URDF import accepts. A URDF's root link remains implicitly fixed to its parent frame at import time; whether that frame itself is static or free is a property the simulation layer assigns afterward.

## 3. State representation and coordinates

1. `robot-model`'s `JointKind` enum (currently `Revolute | Continuous | Prismatic | Fixed`, each ≤1 DOF) MUST gain `Free` (6 DOF: 3 translation + 3 rotation, quaternion-valued orientation) and SHOULD gain `Ball` (3 DOF, quaternion-valued, no translation) to represent a floating base and spherical joints respectively. This is the single largest structural gap identified against MuJoCo [MuJoCo §1]: without it, `robot_sim::articulated::ArticulatedBody` cannot represent anything but a base rigidly welded to world, which is why the existing G1 simulation runs "bolted at the pelvis."
2. A profile's position-coordinate count (`nq`-equivalent) and velocity/DOF count (`nv`-equivalent) MUST be tracked as distinct quantities once `Free`/`Ball` joints exist, mirroring MuJoCo's own `qpos`/`qvel` width mismatch for exactly the same reason (a unit quaternion needs 4 numbers to represent 3 rotational DOF) [MuJoCo §1]. `robot_types::frames::Quat` already exists and already forbids the bare four-element array MuJoCo's own convention would otherwise invite (`SPECS.md` §7.2); the new joint types MUST use it, not a raw `[f64; 4]`.
3. A `Free` joint's velocity representation MUST follow MuJoCo's own documented asymmetry — global-frame linear velocity, body-local-frame angular velocity — rather than inventing a different convention, since that asymmetry is described in MuJoCo's own documentation as "correct use of the topology of quaternions," not an arbitrary choice [MuJoCo §1].
4. Kinematic loops remain disallowed in the joint tree; a closed loop MUST be modeled as an equality constraint (Section 7), never as an extra tree edge — this matches both MuJoCo's own design [MuJoCo §1] and this project's existing tree-only `RobotProfile::validate`.
5. C-04 (canonical frames/gravity/quaternion ordering, `docs/decisions/0002`) remains open. Nothing in this section resolves it; `Free`/`Ball` joints carry their own local quaternion exactly as `Quat` already requires, independent of any project-wide frame convention.

## 4. Dynamics: mass matrix, bias forces, integration

1. The mass-matrix-and-bias-force structure MUST remain the Composite Rigid Body Algorithm (for `M`) plus Recursive Newton-Euler with zero acceleration (for the bias force `c`), the same pattern `robot_sim::articulated`'s existing `ArticulatedBody::inverse_dynamics` already implements. This is not a new requirement so much as a confirmed one: the research agent read MuJoCo's own `mj_rne`/`mj_crb` directly and found the identical gravity-as-fictitious-base-acceleration trick (`a_0 = -g`, sign and all) our RNE already uses [MuJoCo §2] — independent, strong confirmation that this session's hand-derived implementation is structurally the same algorithm MuJoCo's engine runs, not merely "a" Featherstone-style RNE that happens to also work.
2. One coordinate-frame divergence from MuJoCo MUST be recorded, not silently carried: MuJoCo's own CRBA/RNE run in **global** coordinates (deliberately, to share machinery with collision detection), with local per-subtree-COM frames used only for floating-point accuracy [MuJoCo §2]. `robot_sim::spatial`/`articulated` work entirely in each body's own **local** frame via recursive `RigidPose` composition — closer to the textbook Featherstone convention than to MuJoCo's actual engine. Both are valid; this document records the choice (local frames, continuing the existing implementation) rather than reversing it to match MuJoCo exactly, since nothing in the GPU-batching or fidelity requirements depends on which frame convention is used internally.
3. The semi-implicit Euler integrator this session built and validated (`MultibodyState::step`) MUST NOT remain the only integrator. MuJoCo's own "simple" default integrator is not plain semi-implicit Euler — it already folds joint-damping derivatives into an implicit solve by default — and MuJoCo offers `implicit`/`implicitfast`/`discrete` variants specifically because stiff systems (small distal masses, large effective torque ratios — exactly what the real G1's wrists are) need more than explicit integration can stably provide at a usable timestep [MuJoCo §5]. This gives a precise, textbook name and mechanism for the dt-sensitivity this session found empirically (stable at `dt=1e-4`, diverging by ~1.3 simulated seconds at `dt=5e-4`): the fix is an implicit-in-velocity term, not merely a smaller `dt`.
4. `robot-sim` MUST implement, at minimum, an integrator equivalent to MuJoCo's `implicitfast` (semi-implicit position update, implicit-in-velocity for joint damping and passive forces, dropping only the most expensive Coriolis/RNE-derivative term) before any claim of "stable at a usable timestep on a real humanoid" is made. A full `implicit`-equivalent (including RNE derivatives) and an RK4 option SHOULD exist for long-horizon energy-conservation-sensitive use (free-floating tumbling bodies specifically; MuJoCo's own docs note `implicitfast`'s dropped gyroscopic term "mildly damps" a standalone spinning free body, which is now directly relevant once `Free` joints exist) [MuJoCo §5].
5. Integrator choice MUST be a per-run, queryable fidelity knob (Section 12), not a compile-time constant.

## 5. Contact and constraint solver

1. Contact and all equality constraints (Section 7) MUST be solved as one problem, following MuJoCo's own reformulation: a convex optimization (QP for pyramidal friction cones, a conic program for elliptic cones) over constraint forces, not a classical LCP [MuJoCo §3]. MuJoCo's own stated rationale — dropping strict complementarity lets soft/penetrating contact be modeled as physically correct rather than a numerical defect, and avoids LCP-with-friction's worst-case NP-hardness — is adopted as this project's rationale too, not merely reported as MuJoCo's opinion.
2. A soft-constraint mechanism equivalent to `solref`/`solimp` MUST exist: a per-constraint impedance value controlling how strongly a violation can generate force, and a reference-acceleration spring-damper on the constraint residual itself (not on the bodies), parameterized by a time-constant/damping-ratio pair in the common case and raw stiffness/damping in the direct case (needed for e.g. perfectly elastic restitution) [MuJoCo §3].
3. `robot-sim` MUST implement the internal safety check MuJoCo itself relies on: a constraint's effective time-constant must exceed roughly twice the simulation timestep, or the constraint becomes too stiff for the integrator to resolve stably — MuJoCo's own documentation names this directly as the mechanism that prevents exactly the kind of timestep/stiffness divergence this session hit empirically [MuJoCo §3]. `robot-sim` currently has no analogous check anywhere.
4. Both friction-cone models (pyramidal and elliptic) SHOULD be supported, with the explicit, counter-intuitive fact from Section 3's research recorded in the implementation's own documentation: a pyramidal cone with more edges does not converge to the elliptic-cone solution for soft contacts — they define genuinely different soft-contact dynamics, not points on one approximation-quality spectrum [MuJoCo §3]. Contact dimensionality (`condim` 1/3/4/6) MUST be a per-contact, queryable fidelity parameter (Section 12).
5. At least two solver algorithms MUST be available: a Newton-style method (exact second derivatives, few iterations needed, MuJoCo's own documentation for MJX specifically endorses "often just one" iteration as sufficient for RL-training fidelity [MJX §15]) and a Gauss-Seidel/CG-style iterative method retained for comparison and for any execution context where Newton's per-iteration cost is unaffordable. Classical PGS MAY be retained for the CPU reference backend; it MUST NOT be required of the GPU-batched backend, since MJX-JAX itself drops PGS specifically because its strictly-sequential per-constraint update does not vectorize the way CG/Newton's linear algebra does [MJX §12] — direct precedent for the general batching rule Section 11.1 states.
6. Solver iteration count and convergence tolerance MUST be per-run, queryable fidelity knobs (Section 12).
7. Warm-starting (initializing each step's solve from the previous step's constraint forces, falling back to the unconstrained solution if it scores worse) SHOULD be implemented; MuJoCo's own documentation credits it with eliminating "nearly the entire cost of the constraint solver" in a quiescent scene [MuJoCo §3].

## 6. Collision detection pipeline

1. A multi-stage pipeline MUST exist: broad-phase candidate-pair generation, a mid-phase per-pair bounding-volume test, and a narrow-phase dispatch keyed by geometry-type pair — mirroring MuJoCo's own sweep-and-prune-then-BVH-then-dispatch-table structure [MuJoCo §4]. `robot_sim::contact::ContactBody`'s existing single hard-coded point-vs-ground-plane model satisfies none of this and remains a separate, smaller benchmark (Section 1.6 does not retire it).
2. Primitive collision shapes (sphere, box, capsule, cylinder, plane at minimum) MUST each have an exact narrow-phase routine; general convex shapes (meshes, replaced by their convex hull for collision purposes, matching MuJoCo's own `qhull`-based approach [MuJoCo §4] and §9 below) MUST fall back to a generic convex-convex algorithm — GJK for distance/separation, EPA for penetration depth, matching MuJoCo's own native pipeline [MuJoCo §4] — rather than a bespoke per-pair routine for every possible shape combination.
3. A body-pair exclusion mechanism equivalent to `contype`/`conaffinity` bitmasks and parent-child/same-body exclusion MUST exist, so adjacent-link self-collision (e.g. a URDF-imported humanoid's own forearm and upper arm) does not require per-model manual exclusion lists.
4. Collision margin (a surface-inflation distance below which contacts are detected but only generate force below a tighter threshold) and gap (detection-only, for adhesion-style effects) SHOULD both be supported as per-geometry-pair parameters, matching MuJoCo's own [MuJoCo §4].
5. Signed-distance-field collision (non-convex shapes via SDF gradient descent, MuJoCo 3.x) is an explicit non-goal (Section 1.6).

## 7. Actuators, tendons, equality constraints

1. An actuator MUST be describable as the composition of three independent, orthogonal choices, matching MuJoCo's own model exactly because it is the cleanest known factoring that still expresses a torque motor, a position servo and a velocity servo as the *same* underlying mechanism (an affine gain/bias function) rather than three special cases [MuJoCo §6]:
   - **Transmission**: how the actuator's scalar output maps into joint-space force (direct joint, tendon, site, slider-crank).
   - **Activation dynamics**: whether the actuator carries internal state between its command and its output (none, for a direct torque motor; a first-order filter, for a more realistic motor response).
   - **Gain/bias**: the function from (activation, length, velocity) to scalar force. An affine gain/bias (`force = gain·input + bias`, `bias = const + kp·length_error + kv·velocity`) already expresses both a position servo and a velocity servo as special cases of one formula — `robot-model`'s existing `ActuatorSpec`/`PdGains` should be re-examined against this factoring rather than extended ad hoc.
2. Equality constraints (connect/point-to-point, weld/full rigid lock, a polynomial joint-coupling equivalent to and strictly more general than URDF's rejected `mimic`, and a tendon-length equivalent) MUST be solved through the *same* constraint solver as contact (Section 5), not a separate mechanism — this is a MuJoCo design choice (one unified Jacobian/optimization problem) [MuJoCo §6], and splitting it into two solvers would be a step backward from what research found, not a simplification.
3. A weld constraint's orientation residual MUST use an exponential-map-style encoding (`sin(θ/2)·axis`, matching MuJoCo's own choice) rather than a naive Euler-angle or raw-quaternion-difference residual, specifically to avoid wrap-around error at large angles [MuJoCo §6].
4. Tendons (spatial, with pulleys and geometric wrapping around obstacles; fixed, a linear combination of joint positions) MAY be deferred past the first GPU-batched milestone — no part of a humanoid locomotion/balance task strictly requires them — but the actuator factoring of item 1 MUST NOT preclude adding them later as another transmission type.

## 8. Passive forces

1. Joint/tendon spring-dampers (position- and velocity-dependent only — never dependent on control or acceleration, which is exactly why they are identical inputs to both forward and inverse dynamics [MuJoCo §7]), dry friction loss, and a per-body gravity-compensation term MUST all be representable.
2. A spring-damper's sign-preservation condition (for a polynomial stiffness/damping curve: non-negative leading coefficients, discriminant bound) SHOULD be checked at profile-validation time rather than left as an unenforced convention a bad parameter set can silently violate — MuJoCo's own documentation flags this exact failure mode (silent energy injection) without preventing it [MuJoCo §7]; `RobotProfile::validate` already has a pattern (`InertiaTensor::is_physically_plausible`) this can follow.
3. Passive-force derivatives (with respect to velocity, specifically) MUST be available to whichever implicit integrator Section 4 requires — this is literally why MuJoCo's own documentation frames implicit integration's primary motivation as "systems with substantial damping in tendons and actuators" [MuJoCo §5, §7], not contact stiffness.

## 9. Sensors

1. The sensor types already named across `robot-types`/`robot-model`/`robot-perception` (joint position/velocity, IMU-style accelerometer/gyro, force/torque, contact) cover the robotics-relevant subset of MuJoCo's 55-type catalog [MuJoCo §8]; this revision does not require matching the full catalog (frame sensors on arbitrary objects, subtree center-of-mass/momentum sensors, geometric-relationship sensors) unless a specific task needs one.
2. Whether a per-sensor noise model is applied by the physics engine itself or left to the caller MUST be an explicit, documented choice — not left ambiguous the way MuJoCo's own `sensor_noise` field is (the research agent confirmed the field exists but could not confirm, without reading `engine_sensor.c` further, whether it is auto-applied [MuJoCo §8, flagged unverified]). This project's own existing convention (`StampKind`, explicit sampling-vs-arrival timestamps) already treats delay/uncertainty as data the producer must declare, not something the consumer infers; sensor noise should follow the same discipline — generated at a declared point in the pipeline, recorded as such.

## 10. Model compilation and asset import

1. `robot_model::urdf::parse_link`'s current behavior — a missing `<inertial>` element silently becomes `MassProperties::MASSLESS` — is a real, now-named gap against MuJoCo's own URDF-import compiler behavior: MuJoCo's `inertiafromgeom` defaults to `"auto"` (infer mass/inertia from the attached collision geometry's volume and a density when `<inertial>` is absent) specifically because, in its own documentation's words, "a number of publicly available URDF models [have] seemingly arbitrary inertias" [MuJoCo §9]. `robot-model` SHOULD add geometry-based inertia inference as an explicit, opt-in import mode (never a silent default change to existing behavior, consistent with `SPECS.md` §7.1's "reject unsupported constructs explicitly" ethos already governing this importer) rather than leaving every under-specified link massless.
2. A static-body-fusing pass (collapsing a chain of links connected only by `Fixed` joints into their parent, matching MuJoCo's own `fusestatic` default for URDF import specifically [MuJoCo §9]) MAY be added as a separate, explicit transform a caller opts into — the vendored G1 fixture's 39 links/38 joints (versus what MuJoCo's own compiler would produce from the identical URDF) is the concrete, already-present example this would change. This MUST remain optional: `robot-viewer`'s inspection use case benefits from every named link surviving import; a GPU-batched dynamics pass benefits from fewer, fused bodies.
3. Mesh collision geometry MUST be reduced to a convex hull before any narrow-phase collision routine sees it, matching MuJoCo's own compile-time `qhull` step [MuJoCo §4, §9] — never at simulation time, and never passing a full concave mesh into a convex-convex collision routine.

## 11. GPU-batched execution architecture

### 11.1 Batching strategy

Two materially different, both real-world-validated architectures exist for batching a parent-before-child tree recursion like CRBA/RNE/ABA across thousands of environment copies [MJX §14]:

- **(a) Vectorize each tree-level operation across the environment axis**, keeping the recursion itself as a trace-time (not run-time) loop over tree depth. This is MJX-JAX's actual approach: every environment runs the identical operation sequence every step, varying only in data, never in control flow — which is exactly why MJX-JAX must make contact counts static per environment (11.2) rather than variable.
- **(b) One thread (or kernel invocation) per environment**, each running an ordinary, unmodified sequential recursion — branches and all — relying on the GPU's own SIMT hardware to run many such threads concurrently. This is the CUDA/Warp-style model, and MuJoCo's own team built a second implementation (MJX-Warp) specifically because MJX-JAX's branching/contact-count limits became the throughput bottleneck on complex scenes [MJX §12, §14] — real-world evidence that (a) has a real ceiling (b) does not share.

**Decision**: `robot-sim`'s GPU-batched backend MUST target strategy (b), one thread per environment running `robot_sim::articulated`'s existing recursive ABA/RNE structure largely unchanged, rather than restructuring it into per-tree-level batched tensor operations. Rationale: (b) requires reusing the dynamics algorithm already built and validated this session rather than rewriting it into a different shape; (b) is the better-scaling of the two per MuJoCo's own documented reason for building MJX-Warp at all; and (b) is the model CubeCL's kernel-launch abstraction (`Unit`/`Plane`/`Cube`/`Hypercube`, Section 11.3) is actually built around — a `Cube` (thread-block) per environment, or a `Unit` (thread) per environment for small models, is a direct, idiomatic fit for CubeCL's programming model, whereas strategy (a) would require restructuring every operation in `robot_sim::spatial`/`articulated` into explicitly-batched array operations the way JAX's `vmap` does automatically and CubeCL does not. This is a `reproduced_in_sim`-track decision, not a `validated_on_hardware` one: Appendix B records it as open until a working prototype measures real throughput against strategy (a) on our own fixtures, since research found **no existing precedent, in Rust or otherwise, of strategy (b) applied to a tree-recursive rigid-body solver specifically** [Rust-GPU §16] — the closest found precedent (an N-body simulation in a Bevy compute shader) is embarrassingly parallel, not tree-recursive, and is weaker evidence than either of MJX's two production implementations.

### 11.2 Static contact budgets are a fidelity cost, not a free technique

Whichever batching strategy is used, variable per-environment active-contact counts MUST be handled the way MJX itself handles them: a fixed, model-level maximum contact-slot count, computed once (not per step, not per environment), with every step evaluating the full fixed set and masking/excluding inactive slots downstream via the ordinary margin mechanism. This is REQUIRED to state explicitly, because research found it is not merely a padding technique: when the real candidate-contact count exceeds the configured budget, MJX silently drops the least-penetrating real contacts via a top-k selection to fit the fixed slot count [MJX §12] — a genuine behavioral divergence from an unbounded CPU reference under contact-dense scenes. `robot-sim` MUST report, not silently absorb, every step on which the real contact count exceeded the configured budget (a counter, at minimum, following the same "bounded capacity with exhaustion reporting, never silent overwrite" pattern `SPECS.md` §7.6 already requires of experience storage). The contact-slot budget MUST be a per-run, queryable fidelity/sizing parameter (Section 12), sized against the planned environment count the way MJX's own documentation explicitly warns callers to do [MJX §12].

### 11.3 Rust-native GPU compute path

1. **CubeCL is the primary candidate** for authoring the GPU-batched dynamics/contact kernels directly in Rust. Research confirmed it has genuine SIMT-shaped control flow — runtime loops, conditionals, `switch`/`match`, and barrier/synchronization primitives (`sync_cube`/`sync_plane`) — not merely elementwise/matmul operations, across CUDA, ROCm, Metal and WebGPU/Vulkan backends, including a real CPU (LLVM) backend usable without a GPU present [Rust-GPU §16]. It reaches CUDA natively (via `cubecl-cuda`), which matters if training hardware is NVIDIA and a CUDA-backed neural-net policy (via Burn) needs to share a GPU context with the physics kernels.
2. This recommendation carries a named, unresolved risk that MUST stay open in Appendix B rather than be glossed over: research found **zero examples**, in CubeCL's own repository, issue tracker, or anywhere else searched, of anyone using its control-flow primitives for a non-neural-network, physics-shaped, or iterative-constraint-solve workload [Rust-GPU §16]. Every example and tutorial found is NN-primitive-shaped (activation functions, normalization, reduction-as-a-teaching-exercise). The language's documented capability and the ecosystem's actual exercised use are two different things, and this document does not conflate them. Concrete, currently-open maturity issues were also found and MUST be tracked before committing further engineering to this path: a WebGPU validation failure that silently returns wrong data rather than erroring (a specifically bad failure mode for a physics engine), a Vulkan/SPIR-V thread-local-array size limit, and backend-specific driver/toolchain issues on recent CUDA and ROCm releases [Rust-GPU §16].
3. **`wgpu` with hand-written WGSL compute shaders is the fallback**, used directly (bypassing CubeCL/Burn) for any kernel CubeCL cannot express or cannot yet express reliably. `wgpu` has real, if narrower, non-rendering-compute precedent in the wild via the Bevy ecosystem (a compute-shader cellular-automaton example, a GPU-readback example matching exactly the buffer-readback pattern a physics step needs to return state to the CPU/RL side, and at least one GPU N-body simulation) — but every precedent found is embarrassingly parallel (grids, independent pairwise sums), never tree-recursive with a parent-before-child dependency, which is a materially harder pattern than anything found actually implemented in `wgpu` [Rust-GPU §16]. `wgpu` has **no CUDA backend at all** (Vulkan/Metal/DX12/WebGPU/OpenGL only) — on NVIDIA hardware it reaches the GPU only through Vulkan, which is a real architectural cost if a CUDA-backed policy network needs to interoperate with it (cross-API memory sharing between Vulkan and CUDA is possible but nontrivial, not the zero-cost case a shared CUDA context would be).
4. **Candle's custom-kernel path (`cutile`) is not recommended** for this use. It is CUDA-only (no AMD, no Apple, no CPU fallback), requires GPU compute capability `sm_80`+ (Ampere or newer) and a heavier native toolchain (CUDA 13.2+, `clang`, NVIDIA's own `tileiras` compiler) at kernel-build time, and is structurally scoped to implementing one custom tensor operation inside Candle's existing op-graph — a narrower, newer, more hardware-constrained path than CubeCL's, with no found precedent beyond Candle's own introductory guide [Rust-GPU §16].
5. **No existing Rust-native GPU-batched rigid-body physics engine was found to build on or benchmark against** — a credible-looking "RapierGPU" project surfaced in search was a single-day, one-star, eight-months-abandoned experiment, and no other candidate repository was found at all [Rust-GPU §16]. This document records that whatever gets built under this section is, as far as research could determine, close to first-of-its-kind in the Rust ecosystem specifically — a materially different risk profile than this project's other "author a scoped interim, validated independently" decisions have had (the IK solver, the linear algebra, the URDF importer, this session's own CPU ABA/RNE — every one of those had an established non-Rust reference implementation to validate numerical correctness against; a Rust-native GPU-batched contact solver does not, beyond the CPU reference backend this project builds for itself in 11.4).
6. A C/CUDA-authored kernel, or a binding to an existing foreign GPU physics library, remains available only through the `SPECS.md` Section 2.1 foreign-dependency exception procedure. This document does not request that exception and does not assume it will be granted; Sections 11.3 items 1-5 are the default path pending that procedure, not a placeholder for it.

### 11.4 CPU reference backend (required, not optional)

1. A single-instance, full-control-flow CPU implementation MUST exist independent of whatever GPU-batched backend is built, and MUST remain the correctness oracle the GPU backend is checked against — mirroring exactly how MJX-JAX's own test suite is checked against CPU MuJoCo [MJX §12], and continuing the pattern this session already established (`robot_sim::articulated::ArticulatedBody`, validated by closed-form/round-trip/energy tests with no GPU involved at all).
2. The CPU reference backend MUST NOT be retired once a GPU backend exists. It is the fixture every fidelity-tier definition (Section 12) and every cross-backend agreement test (Section 14) is measured against.

## 12. Variable fidelity as a first-class interface

### 12.1 Enumerated knobs

The following MUST each be an explicit, per-run, queryable parameter of a simulation configuration — never a compile-time constant and never silently defaulted without the default being documented:

| Knob | Range of effect | Research basis |
| --- | --- | --- |
| Timestep | Smaller = more accurate, proportionally slower; too large relative to constraint stiffness = unstable (Section 5.3) | `[MuJoCo §15]` |
| Integrator | Euler-equivalent (cheapest, needs implicit damping per Section 4.3-4.4 to be usable at all) through RK4-equivalent (costliest, best long-horizon energy behavior for tumbling free bodies) | `[MuJoCo §5, §15]` |
| Solver algorithm | Newton-equivalent (few iterations, more per-iteration cost) vs. CG-equivalent (more iterations, cheaper each) | `[MuJoCo §3, §15]` |
| Solver iteration/tolerance budget | MuJoCo's own documentation endorses "often just one" Newton iteration as sufficient for RL-training fidelity specifically — i.e. this knob's acceptable range is *task-dependent*, not a universal accuracy dial | `[MJX §15]` |
| Contact dimensionality (`condim`) | 1 (frictionless) through 6 (+torsional +rolling); strictly more solver cost for strictly more physical realism | `[MuJoCo §3, §15]` |
| Contact-slot budget (GPU backend only) | Trades "contacts silently dropped under load" against memory/throughput (Section 11.2) | `[MJX §12, §15]` |
| Collision margin/gap | How early a near-contact is detected/reported vs. force-generating | `[MuJoCo §4, §15]` |

### 12.2 Named fidelity tiers (this project's addition)

MuJoCo itself exposes none of the above as named tiers — research confirmed only an unnamed, independently-tunable knob pile, with its own documentation reading as "here is a direction to turn each knob," not "here are three presets" [MuJoCo §15]. NVIDIA's Isaac Lab comes closer with a named, documented two-way solver choice (PGS vs. TGS) and a whole family of named, swappable solver *backends* (PhysX, MJWarp, Kamino, VBD, MPM), each with its own tuning guide [IsaacLab §15]. Brax's four pipelines (MJX, Generalized, Positional, Spring) are the closest found precedent for a single engine exposing an explicitly speed/fidelity-ordered set of named choices behind one interface [Brax §15, §17].

Following Brax's precedent rather than MuJoCo's, `robot-sim` SHOULD define named fidelity tiers as a first-class, documented part of its configuration surface (exact names and per-tier knob settings are an implementation decision, tracked open in Appendix B, not fixed by this document) — for example, a cheap tier suited to early-training rollout volume, a tier matching this session's own validated CPU reference settings, and a tier enabling the costlier implicit/RK4/elliptic-cone/high-iteration settings for final acceptance-style evaluation. Whatever the eventual names, every tier MUST be expressible purely as a named bundle of the Section 12.1 knobs — no tier may introduce behavior unreachable through the individual knobs, so a caller can always start from a named tier and override one knob without losing the ability to reason about what changed.

## 13. Backend-agnostic architecture

### 13.1 The stable, caller-facing interface

`robot_sim::env::Environment` (already implemented: `observation_width`, `action_width`, `reset`, `step`) is the `robot-sim` analogue of Brax's `Env` trait (`reset`, `step`, `observation_size`, `action_size`) [Brax §17]. This interface MUST remain backend-independent: no method signature, associated type, or field may vary by whether the implementation underneath is the CPU reference backend or a GPU-batched one. `robot-learn`, `robot-control`, `robot-viewer` and `robot-cli` MUST depend only on this trait (or its eventual batched generalization, 13.2) — never on `robot_sim::articulated`, `robot_sim::spatial`, or any future GPU-backend module directly.

### 13.2 The narrow backend plug-point

Following Brax's own two-layer design exactly — `Env` (stable) wraps a `PipelineEnv` that selects one of a fixed set of backend modules by name, and from then on calls exactly two functions on it, `pipeline.init` and `pipeline.step`, with every backend-specific detail living behind those two calls and nothing else [Brax §17] — `robot-sim` MUST define an equivalently narrow internal trait (a "pipeline" or "backend" trait, exact name an implementation decision) with the minimum surface needed to implement `Environment` on top of it: something equivalent to `init(profile, config) -> BackendState` and `step(&BackendState, action) -> BackendState`. The CPU reference backend (11.4) and the GPU-batched backend (11.1-11.3) MUST both implement this same narrow trait, and `Environment`'s own implementation MUST be written once, generically, over it — not duplicated per backend.

### 13.3 What MAY legitimately differ by backend, named explicitly rather than hidden

Brax's own `Env` trait exposes `backend: str` as a stable, queryable property — an explicit, honest acknowledgment that backend identity is sometimes observable even though the call signature never changes [Brax §17]. MJX's own documented leaks (an exception raised at load time if a model uses an MJX-unsupported feature; `naconmax`, an MJX-only sizing concept with no CPU-MuJoCo equivalent a caller must learn to size correctly; differentiability present in MJX-JAX, absent in MJX-Warp and CPU MuJoCo alike) are named directly in its own documentation, not discovered by accident [MJX §17]. `robot-sim` MUST adopt the same honesty rather than claim a leak-free abstraction that the strongest found precedent (MJX itself, built by MuJoCo's own team) does not actually achieve:

1. A backend identifier MUST be queryable from any `Environment` implementation.
2. Any backend-specific sizing parameter (the GPU backend's contact-slot budget, 11.2) MUST be named and documented as such, not folded silently into a profile or a generic config struct that reads as backend-independent.
3. Differentiability, if ever added to any backend, MUST be declared via a capability query, not assumed present or absent.
4. A model feature unsupported by a given backend MUST cause a loud, named error at construction time (matching MJX's own exception-on-load behavior), never a silent fallback to different physics.

### 13.4 Dependency direction

`robot-sim`'s GPU-batched backend module(s) MAY depend on CubeCL/`wgpu` (Section 11.3); nothing outside `robot-sim` may. This keeps the GPU-compute dependency decision fully reversible and fully contained — consistent with this project's standing pattern of isolating a not-yet-qualified dependency behind the one crate that needs it (`docs/decisions/0004`'s `robot-nn`/`robot-supervisor` extraction is the direct precedent for this kind of boundary).

## 14. Validation and evidence requirements

1. Every claim this document or its implementation makes about `robot-sim`'s own behavior starts at `unverified` per `SPECS.md` §3, promoted only by the evidence that table requires — a MuJoCo/MJX/Brax citation never promotes a claim about our own code, no matter how closely the design follows the cited precedent.
2. The GPU-batched backend's output MUST be checked against the CPU reference backend (11.4) on shared fixtures at matched configuration, following the same spirit as MJX-JAX's own correctness testing against CPU MuJoCo [MJX §12] — agreement within a stated, recorded tolerance, not an assumption of agreement.
3. Every fidelity tier (12.2) MUST have its own energy-conservation and closed-form validation, following the pattern this session already established for the CPU-only solver (hand-derived pendulum closed form, RNE/ABA round-trip, multi-link free-motion energy conservation) — a cheap/fast tier that fails conservation checks a costlier tier passes is a real, reportable fidelity cost (Section 12.1's own framing), not a defect to hide.
4. The contact-slot-exhaustion counter (11.2) MUST be exercised by a test that deliberately exceeds the configured budget and confirms the counter increments rather than the simulation silently continuing as if nothing were dropped.
5. Cross-simulator or cross-engine comparison (against MuJoCo itself, via bindings) remains outside this document's scope and subject to `SPECS.md` Section 2's foreign-dependency exception procedure exactly as `SPECS.md` §9.1 already states; nothing here requests or assumes that exception.

## Appendix C — Relationship to existing `robot-sim` code
