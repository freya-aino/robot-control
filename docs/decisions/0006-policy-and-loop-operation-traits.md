# 0006 — policies and loop operations are traits; `ControlLoop` is generic over them

- Status: accepted
- Date: 2026-10-27
- Touches: SPECS.md §5 (control-path allocation rule), SPECS.md §12 (supervisor fault categories and safe responses), `PLAN.md` Phase 1; `crates/robot-nn/src/policy.rs` (new), `crates/robot-control/src/operation.rs` (new), `crates/robot-control/src/control_loop.rs`, `crates/robot-learn/src/gaussian_policy.rs`, `crates/robot-sim/src/backend.rs` (new), `crates/robot-sim/src/multibody_env.rs` (new), `crates/robot-sim/src/articulated.rs`, `crates/robot-model/src/importer.rs` (new), `crates/robot-supervisor/src/{fault,policy,supervisor}.rs`

## Context

`ControlLoop` held a concrete `policy: Mlp` and had no hook for sampling, seeding or online training. Adding any of those meant editing the loop. `PLAN.md` Phase 1 asks that new policies, loop operations and simulator backends be added as new code, and that the existing test suite pass unchanged. Before this change, a NaN observation or a failing policy panicked inside `tick`, so the seam also had to make failure handling explicit.

## Decision

1. **`Policy` lives in `robot-nn`**, next to `Mlp`, which is its first implementor. `robot-control` already depends on `robot-nn`, so no new crate boundary is introduced. `Policy` is deterministic: `input_width`, `output_width`, `scratch_len`, and `act`, which writes into a caller-owned buffer and `Scratch`.
2. **Stochastic behaviour is a separate extension trait, `StochasticPolicy: Policy`**, with `sample_action(obs, rng, action, scratch) -> log_prob`. Deterministic inference does not carry a sampling path, and a policy with no randomness does not implement it. `GaussianPolicy` implements both; its `sample_action` draws the same noise in the same order as the existing allocating `sample`.
3. **`LoopOperation<P: Policy>` lives in `robot-control/src/operation.rs`** with four hooks, each defaulted: `check_widths` (run once at construction), `before_tick`, `select_action` (default: deterministic `policy.act`, returns `Option<log_prob>`), and `after_tick`, which receives a `TickView` carrying the normalized observation, the raw action before supervision, the command after supervision, the supervisor `Response` and the log-probability. `select_action` is the only hook that chooses the action.
4. **`ControlLoop<A, C, const N, P: Policy = Mlp, O: LoopOperation<P> = NoOp>`** is generic. Dispatch is compile-time (monomorphized), so no `dyn` is on the tick path. The defaults keep `ControlLoop<A, C, N>` naming the same loop as before.
5. **Construction is split**: `ControlLoop::new(config)` is implemented for `O = NoOp` and is what existing call sites use; `ControlLoop::with_operation(config, op)` installs any operation and panics on a configuration error; `ControlLoop::try_with_operation(config, op)` returns `ConfigError` instead. Construction checks, before the first tick:
   - the normalizer width equals `policy.input_width()` (`ConfigError::Normalizer`);
   - the supervisor width equals `policy.output_width()` (`ConfigError::Supervisor`);
   - the adapter width equals both `policy.input_width()` and `policy.output_width()` (`ConfigError::Adapter`, with an input/output component). `HardwareAdapter` has one width for feedback and commands, so policies with unequal input and output widths cannot be connected to the current adapter contract;
   - the operation's `check_widths` accepts the loop's widths (`ConfigError::Operation`).

   Operation state is reached through `operation()` and `operation_mut()`.
5a. **Composition**: `(A, B)` is a `LoopOperation`. Only `A::select_action` chooses the action; both elements receive `before_tick`, `after_tick` and `check_widths`. Put the selecting operation first. `(SamplingToggle, ExperienceRecorder)` samples and records the sampled action and its log-probability.
6. **Allocation rule**: all buffers are allocated in construction. `SamplingToggle` allocates its RNG in `new`. `ExperienceRecorder` allocates a fixed ring in `new`, overwrites the oldest slot when full, and exposes the held transitions oldest first through `get`, `iter`, `last` and `clear`, so a learner can drain them between ticks. The recorder stores the raw (pre-supervision) action and the log-probability, plus the transmitted command. A unit test checks that recording does not reallocate its storage. The loop-level test `the_tick_path_reuses_its_buffers_across_ticks` checks that the feedback, normalized, raw-action and command buffers keep their address and capacity, and the recorder keeps its capacity, over 50 ticks with sampling and recording installed. That test is regression evidence, weaker than a counting allocator: it catches a buffer being replaced, not a transient allocation. A probe with a counting global allocator and a non-allocating adapter measured 0 allocations over 100 ticks for `Mlp + NoOp`, `Gaussian + SamplingToggle`, `Mlp + ExperienceRecorder` and `Gaussian + (SamplingToggle, ExperienceRecorder)`. That probe lives outside the repository because `unsafe_code = "forbid"` in `robot-control` rules out a `#[global_allocator]` in its tests. `LoopbackDevice::send_command` itself allocates, so a loop-level allocation test needs a custom adapter; the loop does not.
6a. **Fault handling**. The loop does not panic on the handled runtime errors, but not every failure produces a command on the wire. Construction rejects incompatible normalizer, supervisor, adapter and operation widths. At runtime, a feedback-poll error, supervisor width error or observation-width error returns without transmission; a non-finite observation or failed action selection is escalated through the supervisor and attempts to transmit its declared safe command. A send failure returns `TickError::Adapter`, with any supervisor fault already recorded.
   - **Non-finite observation** is a supervisor fault. The supervisor gains `Fault::NonFiniteObservation { index }` and `FaultCategory::NonFiniteObservation`. The category is in the must-escalate list next to stale observation and non-finite command, so a `FaultPolicy` that assigns it clamp-and-continue is refused at construction; the conservative default is emergency stop. `Supervisor::reject_observation(input, index, out)` records the fault together with the other input faults of the tick (staleness, comms, mode, temperature, contact) and writes the declared safe command: the last safe command for hold or reject, zeros for e-stop. It never writes a value derived from the bad observation. `ControlLoop::tick` skips the policy and the hooks (there is no valid observation to give them), transmits the safe command wherever a normal tick would transmit, and returns `TickError::NonFiniteObservation { index }`.
   - **Policy or operation failure** (`select_action` returns an error) is treated as a non-finite command. The loop fills `raw_action` with NaN and runs the normal supervisor check, which records `NonFiniteCommand` per joint and applies the declared response (zeros under the conservative default). The safe command is transmitted, and the loop returns `TickError::Policy`. `after_tick` does not run.
   - **Width errors** at tick time return `TickError::ObservationWidth` and transmit nothing, because the observation itself is unusable and the supervisor has no valid input to check.
   - **Error precedence**: if transmission fails during either escalation path, the caller gets `TickError::Adapter` rather than the observation or policy error. Tests use a transmit-refusing replay adapter to check both paths; the fault is still visible in `supervisor_log()`. A caller that needs the original cause should read the log.
   - A NaN action returned by a policy with no error is passed through to the supervisor as `NonFiniteCommand`, exactly as a normal tick does.
6b. **Hook failure semantics**: hooks are not guaranteed to be paired. A tick ends at the first failing stage and only the hooks of stages that ran have fired. No hook runs for a failure before normalization. If `select_action` fails, `before_tick` has run and `after_tick` will not. If the supervisor or the transmission fails, `before_tick` has run and `after_tick` will not, so a sampled action whose transmission failed is not recorded. `after_tick` runs only for a completed tick. This is documented on `LoopOperation` and `ControlLoop::tick` and tested.
7. **Sampling, seeding and online training are operations, not loop fields.** The loop does not know which operation is installed.
8. **`Backend` (robot-sim) and `ModelImporter` (robot-model) follow the same pattern.** `Backend: Environment` adds one queryable `backend_name`, so backend identity is visible rather than hidden (ADR 0005 §6). `ModelImporter` has an associated `Error` type, and `UrdfImporter` wraps the existing loader without changing it. `Backend` is implemented for `PendulumEnv` (`cpu-pendulum`) and for `MultibodyEnv` (`cpu-multibody`), which wraps the same `MultibodyState::step` that `robot sim multibody` uses. Its observation is `q` followed by `qd`; its action is one torque per degree of freedom; `reset` draws each joint within a spread of the home posture from the seed. `MultibodyEnv::new` rejects a home posture whose length differs from the body's position width (`WidthMismatch`) instead of panicking later.
   - **Step failure**: a step the solver rejects (a non-finite or wrong-width torque, or a solve that fails) is reported as `physics_failure`, and the state is left unchanged. This is transactional: `MultibodyState::step` computes the new state and only commits it on success.
   - **Limit**: a step that the solver accepts but that produces non-finite `q` or `qd` is reported as `physics_failure`, and the state is then non-finite. That is a changed state, not a rolled-back one. Callers must check `physics_failure` before using the observation, as with the pendulum.
   - The multibody tests compare the trait-object trajectory with a state stepped by hand against the same body.
8a. **Solver change**: `ArticulatedBody::forward_dynamics` had three `.expect` calls on the joint-inertia solve that panicked once a diverged state overflowed the intermediate products. They now return the new `DynamicsError::SingularJointInertia`. Results for valid inputs are unchanged (the solves are the same calls); only the failure path differs. `Backend` maps it to `physics_failure`.
8b. **Qualification behaviour**: `MultibodyEnv` adds no contact model. The floating-base G1 therefore falls without bound through the backend, exactly as it does in `robot sim multibody --floating`. A test records this and must be replaced by a pelvis-above-plane assertion when ground contact lands (plan Step 4). The wrapper does not claim a floor.

## Consequences

- Existing tests in `robot-control`, `robot-nn`, `robot-learn`, `robot-model` and `robot-sim` are unchanged. Two existing test-side lines did change: the loop over bad fault categories in `robot-supervisor/src/policy.rs` tests gained a `NonFiniteObservation` entry, and `articulated::tests` became `pub(crate)` with `double_pendulum` made `pub(crate)` so `multibody_env` can reuse it. Both edits are additive.
- A `Mlp` policy cannot be used with `SamplingToggle`, because `Mlp` is not `StochasticPolicy`. This is a compile-time error by design.
- `ExperienceRecorder` is a storage hook, not a learner. The training loop that consumes it is future work (Phase 3 / Step 2 onward).
- `robot-supervisor`'s `FaultCategory` gains a variant. Every match on it lives in that crate; `ALL_CATEGORIES`, the response table, `MUST_ESCALATE` and `conservative_default` were updated together.

## What this does not change

- For valid observations and a working policy, `ControlLoop` behaviour is unchanged: the same normalize, infer, supervise, transmit sequence runs, with `select_action` and the two observation hooks added around it.
- What changes is failure handling: a NaN observation or a failing policy used to panic and now yields a `TickError` after the supervisor has chosen a safe command (see 6a). Construction now rejects normalizer, supervisor, adapter-input, adapter-output and operation width mismatches that could previously produce a loop which errored on every tick.
- SPECS.md §2 (std-only default closure, ADR 0003) is unaffected: no new dependencies.
